# 단일 Agent vs Multi Agent 비교 실험 — 사전 프로토콜

> 이 문서는 **결과를 보기 전에** 조건·지표·판정 기준을 확정해 커밋한다 (기존 골드 평가와 같은 방식).
> 실험을 돌린 뒤에 지표나 기준을 바꾸지 않는다. 바꿔야 하면 변경 이력으로 남기고 원래 기준의 결과를 함께 보고한다.
> 결과는 이 문서가 아니라 `docs/single_vs_multi_agent_results.md`에 쓴다.

## 1. 질문

Decision Agent 하나로 충분한가, 독립적인 Critic Agent를 별도로 두는 Multi Agent 구조가 실제로 잘못된 집행을 줄이는가?
그리고 그 효과가 "검토 단계가 있어서"인지 "검토자가 독립된 별도 Agent여서"인지.

## 2. 비교 조건 (세 조건은 같은 1차 판정에서 나온다 — 짝지은 비교)

| 조건 | 구성 | 집행되는 판정 |
|---|---|---|
| **A. 단일 Agent** | Decision Agent의 1차 판정만 (검토 없음) | 1차 판정 |
| **B. 단일 Agent + 자기검토** | 같은 Agent가 같은 대화 안에서(같은 모델·같은 도구·같은 이력) 자기 판정을 다시 점검하고, 필요하면 `record_decision_tool`을 다시 호출해 수정 | 자기검토 후 판정 |
| **C. Multi Agent** | 1차 판정 + 독립 Critic (현재 운영 구조). Critic이 반박하면 집행 보류(`HELD`) | Critic 승인이면 1차 판정, 반박이면 **보류(집행 안 함)** |

- 세 조건은 케이스·반복마다 **하나의 1차 판정을 공유**한다. 1차 판정은 `decision.make_final_decision()`을 수정 없이 호출해 얻고(A, C), B는 그 호출에서 모델이 쓴 대화 이력을 그대로 이어받아 한 턴 더 진행한다. LLM 실행 변동이 조건 간 차이에 섞이지 않게 하기 위함이다.
- **B의 자기검토 지침**은 Critic의 "검토 원칙"과 같은 내용을 쓴다(정량 거절 상향 금지, 근거-정보 모순·근거 없는 조정 점검, 그 외에는 유지). 따라서 B와 C의 차이는 **검토 기준이 아니라 "같은 대화·같은 Agent인가, 별도 호출·별도 Agent인가"** 뿐이다. 지침 전문과 해시는 `scripts/agent/eval_arms.py`(`SELF_REVIEW_PROMPT`)와 결과 `manifest.json`에 기록된다.
- 모델은 운영과 동일(`gemini-flash-lite-latest`), 온도·시드 미지정(API 기본값). 호출당 모델 버전은 기록한다.

## 3. 케이스와 정답

- 평가 케이스·골드는 기존 `scripts/agent/eval_cases_v2.json`을 **그대로** 쓴다 (골드는 정책 문서에서만 도출, 사전 커밋 완료, 변경 없음).
- 지표 대상은 **비-ambiguous 케이스**(63건 중 57건). ambiguous 6건은 지표에서 제외하고 별도 표로만 보인다. 하드캡 케이스는 LLM이 없어 제외한다.
- 정답 = 케이스의 `expected_decision`. 느슨함 순서: `reject`(0) < `conditional`(1) < `approve`(2).

## 4. 프롬프트 조건 (두 가지로 나눠 각각 보고한다)

| 이름 | Decision Agent 지침 | 목적 |
|---|---|---|
| **production** | 현재 운영 지침 | 지금 배포된 시스템에서의 효과 |
| **prefix** (스트레스) | 프롬프트 규칙 4개를 일반화해 추가하기 **직전** 시점(`87e869e^`)의 지침. 요약기·Critic·정책·RAG·모델은 현재와 동일 | 1차 Agent가 더 자주 틀리는 상황에서 검토 단계가 얼마나 도움이 되는가 |

- production은 1차 Agent가 거의 다 맞혀(기존 평가 56/57) 검토 단계가 보여줄 수 있는 오류가 매우 적다. 그래서 오류가 충분히 나오는 prefix 조건을 **스트레스 조건으로 명시**하고 함께 낸다. prefix 조건의 결과는 "현재 운영 시스템의 성능"이 아니라 "1차 Agent가 더 약할 때 검토 구조의 효과"로만 해석한다.
- **주 결론은 prefix 조건(검토 구조의 효과를 볼 수 있을 만큼 오류가 있는 조건)의 풀링 결과로, production 조건은 별도로 병기한다.** 어느 조건도 결과를 보고 주/부를 바꾸지 않는다.
- prefix 조건은 요약기(`business_text.py`)가 현재 버전이다 (규칙 4개 중 요약기 관련 규칙은 포함된 상태). 이 점을 한계로 적는다.

## 5. 반복

- 조건(production, prefix)마다 **2회 반복**(run 1, 2). 같은 케이스·반복은 독립 호출이다.
- 호출 오류로 결과가 없는 케이스·반복은 지표에서 제외하고 개수를 함께 보고한다 (오류 건은 최대 6회까지 재시도).

## 6. 지표 (사전 정의)

케이스×반복 하나를 "인스턴스"라 부른다. 조건별로 아래 결과 분류를 계산한다.

- **결정 일치**: 집행되는 판정 == 골드
- **과잉집행(unsafe)**: 집행되는 판정의 느슨함 순위 > 골드 순위 (예: 골드 거절인데 조건부승인/승인, 골드 조건부인데 승인). 돈이 나가면 안 되는 쪽의 오류.
- **과소집행(strict)**: 집행되는 판정의 순위 < 골드 순위 (대출 기회 손실, 안전한 쪽의 오류)
- **보류**: C에서 Critic이 반박해 집행하지 않은 인스턴스. 1차 판정이 틀렸으면 `보류-오류 차단`, 맞았으면 `보류-오경보`.

| 지표 | 정의 |
|---|---|
| **주 지표: 과잉집행률** | 과잉집행 인스턴스 / 전체 인스턴스 (조건 A, B, C 각각) |
| 오류 차단율 | 1차 판정이 골드와 다른 인스턴스 중, 그 오류가 집행되지 않은 비율 (A는 항상 0, B는 자기검토가 고친 경우, C는 Critic이 반박한 경우) |
| 과잉집행 차단율 | 1차 판정이 과잉집행이었던 인스턴스 중, 집행되지 않았거나 고쳐진 비율 |
| 오경보율 / 훼손율 | 1차 판정이 맞았는데 C에서 보류된 비율 / B에서 틀리게 바뀐 비율 |
| 집행 정확도 | 집행된 인스턴스 중 판정이 골드와 일치한 비율, 그리고 전체 인스턴스 중 "맞게 집행"된 비율 |
| 비용 | 인스턴스당 추가 호출 수·시간·토큰(응답의 `usage_metadata`; 없으면 호출 수만) |

## 7. 통계와 해석 규칙

- 짝지은 비교이므로 조건 간 차이는 **케이스 단위 부트스트랩**(케이스를 재추출, 반복은 케이스에 묶음, 2,000회)으로 95% 구간을 낸다. 표본이 작아 통계적 보증이 아니라 방향과 크기를 보는 용도다.
- 가설은 정해 두지 않는다. **차이가 없거나 Multi가 불리하면 그대로 쓴다.** 결과가 어떻게 나와도 "Multi Agent여야 하는 이유"로 포장하지 않고, 그 결과가 지지하는 범위만 주장한다.
- B에서 수정이 일어난 경우, 수정이 정답 방향인지(고침)/오답 방향인지(훼손)를 모두 센다.
- Critic은 최종 판정을 바꾸지 않고 집행만 보류한다는 현재 정책(C)을 그대로 따른다. 보류된 건은 "집행 안 됨"으로 계산하며, 이후 사람이 어떻게 처리하는지는 평가하지 않는다.

## 8. 알려진 한계 (사전 기재)

1. 골드는 작성자가 정의했고 합성 텍스트·소규모 표본이다. 두 모델 변형 간 차이가 작으면 노이즈와 구분되지 않을 수 있다.
2. 같은 모델(Gemini Flash-Lite)이 두 역할을 맡는다. B와 C의 독립성 차이는 "대화·호출 분리"이고, 서로 다른 모델이 아니다. Multi Agent의 이점을 "서로 다른 모델"로 일반화할 수 없다.
3. prefix 조건은 과거 지침이며 현재 운영 시스템이 아니다.
4. 오류가 적은 production 조건에서는 어떤 조건 차이도 검출하기 어렵다.
5. 지연·비용은 무료/유료 티어, 호출 대기(rate limit 재시도)에 따라 달라 상대 비교용이다.
6. 사람 검토·이후 재판정은 평가 범위 밖이다.
